## H5: describing pages by their catalogue attributes helps more than collapsing them into one category

*Status: designed, not yet run. Every number in the "Observation" section comes from data inspection; the results table in 5.4 is deliberately empty.*

### 5.1 Observation

H4 fixed the new-page problem by replacing each `comp_ID_xxx` column with one `comp_page` count. That works because the column always has training support, but it throws away what kind of competition the user looked at. The data we have not used contains exactly that information.

**The catalogue tables can be joined through the page ID.**

| Link | Match rate |
|---|---|
| `comp_ID_xxx` click titles → `Competition.Comp_ID` | 100% (also for all M4 views) |
| `blog_ID_xxx` → `Blogs.blog_ID` | 100% |
| Participation `Competition ID` → `Competition` | 100% |
| `Comments.Disc_ID` → `Discussion.Disc_ID` | 100% |
| Discussion `Competition ID` → `Competition` | 31.5% (68.5% are `GeneralDiscussion`) |

`comp_ID_WZ0H`, the most popular M4 competition and unseen in training, is in `Competition.csv` with its attributes. A model that sees "a competition with `FeatureE = 2`" rather than "competition WZ0H" can use what it learned from older competitions.

**Attribute columns have the training support that per-page columns lack.** Same measure as H4: the share of M4 page views that land on a value shared by at least 50 training users.

| Column | Per page ID | Per attribute value |
|---|---|---|
| Competition views | 47% | `FeatureE` 100%, `FeatureC` 96%, tag columns not yet measured |
| Blog views | 21% | `Theme` 100% |
| Job views | 30% | not usable: the viewed jobs have no attribute values |

**Attributes seem to be related to retention, but this is not tested.** Among labelled users who viewed a competition (about 33% active next month vs 19.6% overall), the next-month active rate varies by attribute value:

| Attribute | Rate range across values (≥100 users each) |
|---|---|
| `FeatureD` | 33.7% vs 33.9%: none |
| `SecretCode` | 32.4% vs 36.2%: weak |
| `FeatureE` | 31.6% – 43.6% |
| `FeatureB` tags | 29.5% – 49.7% |
| `FeatureC` (34 values; 21% missing) | 27.6% – 49.5% |
| `FeatureF`, `FeatureH` tags | ~24% – 40% |

These rates mix in activity volume (heavy users see more tags and also return more), so they motivate the experiment but do not prove the effect.

### 5.2 Hypothesis

> **H5.** Replacing the single `comp_page` / `blog_page` count with counts split by catalogue attributes improves cross-validated F1 over the H4 per-category tree (0.469), while still generalising to pages not seen in training.

Two sub-hypotheses separate the sources of any gain:

| Sub-hypothesis | Change relative to H4 |
|---|---|
| **H5a: attribute splits** | `comp_page` and `blog_page` counts split by catalogue attribute |
| **H5b: cross-table links** | adds the link between tables: the user joined a competition they viewed, and view→join conversion |

### 5.3 Experiment design

**Features (H5a).**
- **Multi-hot tag counts.** `FeatureA`, `B`, `F`, `G` and `H` hold lists such as `[2, 4]`. A view of a competition adds 1 to each of its tags.
- **Single-valued attributes.** Counts by `FeatureE` value and by `FeatureC` value, with an explicit "missing" bucket. Missing `FeatureC` views retain at 38.4%, so missingness is informative.
- **Rare values pooled.** Values with fewer than 100 training users go into an "other" column. This keeps the width at an expected 25–40 columns rather than 390 and keeps every column supported in M4.
- **Blogs:** counts by `Theme`.
- **Dropped:** `FeatureD`, `SecretCode` (no signal), job attributes, `Participant Type` (constant).

**Features (H5b).**
- Number of distinct competitions viewed, repeat views of the same competition.
- Number of competitions viewed and then joined, and the conversion rate (0 when no views).
- Whether the user posted in a competition-specific vs general discussion.

**Controls.** Only the construction of X changes. Folds, the 216-setting grid, nested cross-validation, class weighting options and the 0.5 threshold are identical to H3 and H4.

**Placebo test.** Randomly permute the competition→attribute mapping (keeping the same number of columns and the same view counts) and re-run. If the placebo gains as much as the real attributes, the improvement comes from splitting the count, not from the attributes.

**Not included in the first run.** Time-relative features (days since a competition started or until it ends). Competition and blog dates use their own masked year and month codes, and we have not verified they line up with the user timeline.

### 5.5 How we will judge it

- **Confirmed** if the mean F1 gain over H4 exceeds one fold standard deviation (~0.011), the paired difference is positive in at least 4 of 5 folds, and the placebo does not match it.
- **Partly confirmed** if the gain is positive but within fold noise, as for H4 (+0.013). We would report it as a simplification or stability gain only.
- **Rejected** if F1 does not improve or the placebo performs as well.

### 5.6 Risks and limitations

- **Confounding with activity volume.** Tag counts grow with the number of competitions viewed. The placebo test addresses part of this; it does not remove it.
- **Noisy small groups.** Several rates above come from 100–300 users; the extremes may be chance.
- **Random-split CV understates the benefit.** As for H4, training and validation share the same months, so the "new page" problem is mild there. A gain on the leaderboard or a time-based split would be stronger evidence.
- **Tree-search cost.** The wider feature set increases the search cost per fold; the grid is unchanged.
- **Inconclusive is possible.** With +0.013 as the H4 gain, a further small gain would be hard to distinguish from noise at 9,026 users.
